## 二、Standards 轴发现

### P1

**[S-P1-1] `src/agents/manager.py:109-116` `trigger_nuclei_upgrade` 使用 `asyncio.create_task` + `add_done_callback` 模式，Task 引用在本地变量 `nuclei_task` 超出作用域后可能被 GC，且回调仅在 Task 完成时触发，不覆盖"Task 被 GC 静默取消"场景。**

V10 阶段 1.2 已将 `enqueue.py` fire-and-forget 全部 await 化，但新增的 nuclei 版本比较代码采用了相同的 fire-and-forget 模式（设计意图：不阻塞 heartbeat 主循环）。虽然有 `add_done_callback` 处理异常日志，但如果 asyncio 事件循环在 Task 执行前回收了它，版本升级静默失败且无告警。

**修法**：将 `nuclei_task` 引用存入模块级 `_BG_NUCLEI: set`，在 `_on_nuclei_done` 回调中 `discard`，参考 V9 `_audit` 模式。

**[S-P1-2] `agent/internal/updater/upgrade.go:217-223` nuclei 下载使用 `io.ReadAll(resp.Body)` 无大小限制，理论上恶意内网服务可返回无限大的 zip 导致 agent OOM。**

实际场景：nuclei CLI zip 约 25-35 MB，但 `io.ReadAll` 不设上限。如果内网 nginx 被篡改返回一个巨型文件，agent 进程 OOM 后 scan 功能消失。`HandleAgentUpgrade`（同文件 :120-180）的 agent 升级有类似问题，但 nuclei 是新链路没有。

**修法**：使用 `io.LimitReader(resp.Body, 200*1024*1024)` 限 200MB 读取上限，超限 `io.ReadAll` 返回错误。

**[S-P1-3] Nuclei 下载走 HTTP 明文（`nuclei_download_base_url: "http://192.168.80.101:8081"`），zip 内容无 hash 校验。**

`upgrade.go:154-158` 注释说明「下载来自可信内网镜像 + Ed25519 命令签名, closing HTTP-in-transit 是未来加固项」。虽然是内网，但 HTTP 明文意味着任何在同一 L2 网段的攻击者可以 ARP 欺骗篡改 nuclei 二进制。Ed25519 签名保护的是「命令来源」而非「二进制内容」。

**修法**：Nacos 中增加 `NUCLEI_SHA256` 字段，Go 端下载后校验 hash；或改为 HTTPS。

**[S-P1-4] `src/agents/rules_sync.py:815-912` 新增的 `sync_nuclei_templates_to_all_agents` 函数与 `sync_rules_to_all_agents` 结构高度重复（~90% 相同）。**

两个函数都是「枚举在线 agent → 逐个推送」模式，差异仅在消息 type 和 payload。这是 Shotgun Surgery 风险：未来修改在线枚举/重试逻辑需改两处。

**修法**：抽 `_fanout_to_agents(build_msg: Callable, label: str)` 共享基函数。

**[S-P1-5] `src/agents/upgrade.py:224-240` Redis cooldown 锁 `set(key, "1", ex=300, nx=True)` 返回 `got` 后，若 lock 返回值检查后、`send_to_agent` 调用前发生异常，锁未释放且无清理路径。**

实际上 5min TTL 提供了自动过期，不算数据泄漏。但如果在 `send_to_agent` 失败时不同时删锁，agent 需等 5min 冷却过期才能重试，运维体验差。

**修法**：`send_to_agent` 失败时 `await redis.delete(lock_key)`，让下次 heartbeat（约 60s）即可重试。

**[S-P1-6] `src/common/config/settings.py:127` `nuclei_download_base_url` 默认值为 `"http://192.168.80.101:8081"` —— 硬编码内网 IP。**

这是实验室环境特定配置，不应出现在代码默认值中。若代码部署到其他环境（如生产网段），agent 可能尝试从不可达的 URL 下载 nuclei 二进制，导致版本对齐静默失败。

**修法**：默认值改为 `""`（空字符串），在 runtime 检查中已处理空 base URL（`trigger_nuclei_upgrade` 返回 early）。空默认值迫使每个部署显式配置。

**[S-P1-7] `src/agents/nuclei_templates.py:76-77` 每次 API 调用创建新的 `AsyncElasticsearch` 客户端，无连接池复用。**

`VulnscanStore` 等其他模块使用持久化 ES 客户端，而 `nuclei_templates` 模块的 `_es()` helper 每次都 `AsyncElasticsearch(...)` → 用完 `await es.close()`。高频调用时（如模板列表页刷新），反复建连/断连增加延迟和 ES 服务端压力。

**修法**：模块级懒加载单例 `_es_client: AsyncElasticsearch | None = None`，或注入共享 client（参考 `VulnscanStore` 模式）。

**[S-P1-8] `src/agents/nuclei_templates.py:125-126` `rebuild_manifest` 先删索引再重建，中途失败则数据全丢。**

`rebuild_manifest` 先 `delete(index="nuclei-templates")` 再 `bulk` 重索引。若 bulk 部分失败（如 ES 内存不足 reject），旧数据已删除，新数据不完整。当前依赖 `_count_manifest` 事后检测行数不匹配，但检测到问题时旧数据已不可恢复。

**修法**：索引到临时索引 `nuclei-templates-next`，成功后 swap alias（`POST _aliases` 原子切换），失败则保留旧索引。

**[S-P1-9] `src/agents/store.py:586-606` `VulnFilter` dataclass 的关键词字段（`cve_keyword`、`hostname_keyword`、`name_keyword`）缺乏 `max_length` 约束。**

这些字段直接进入 ES `wildcard` 查询，10,000 字符的 keyword 会导致极慢的正则扫描。`re.escape` 阻止了 ES 注入但不能防止 DoS。

**修法**：在 `VulnFilter` dataclass 定义中给 keyword 字段加 `max_length=200`，路由层自动拒绝超长输入。

**[G-P1-1] `agent/cmd/agent/main.go:41-43` — config 加载失败后重试吞错。**
`config.Load(cfgPath)` 首次失败后，重试 `cfg, _ = config.Load(cfgPath)`（同一路径），错误被忽略。若返回 nil，agent 退化为带空 `ServerPublicKey` / 空 `AgentID` 的最小内联 config，启动后无法正常注册。
**修法**：删除重试（同路径重读无意义），或正确处理 nil cfg。

**[G-P1-2] `agent/internal/updater/upgrade.go:537-555` — `httpClient(caPath)` 在 CA 加载失败时静默退回系统根 CA。**
`caPath != ""` 时，若 `os.ReadFile` 或 `AppendCertsFromPEM` 失败，函数返回使用系统根 CA 的默认 `*http.Client`，仅打 warning。这意味着本应 pin 到私有 CA 的连接退化为信任系统根 CA，攻击者可用任意系统信任证书中间人。
**修法**：`caPath != ""` 时，加载/解析失败应为硬错误（return nil, error），不静默降级。

**[G-P1-3] `agent/cmd/agent/main.go:256-267` — agent upgrade 成功后先发 success ack，再 goroutine 重启失败后发第二个 failure ack。**
`HandleUpgrade` 成功后立即 `SendUpdateAck("agent", version, true, "")`，同时启动 goroutine 调用 `ApplyStagedAndRestart`。若重启失败，同一 goroutine 发送第二个 ack `ok=false`。服务端收到同一版本两条矛盾的 ack（先 true 后 false），状态模型被破坏。心跳版本不匹配会自愈，但语义错误。
**修法**：重启失败时只 log，不发第二个 ack；依赖心跳 mismatch 触发 re-push。或将 success ack 推迟到重启成功后发。

**[G-P1-4] `agent/internal/comm/client.go:242-245` — WebSocket 重连时 goroutine 泄漏。**
`Connect` 循环的每次迭代 spawn 一个 goroutine 阻塞在 `<-ctx.Done()` 以 close 连接。当 read loop 退出并重连时，旧 goroutine 持续存活（仍阻塞在同一个 ctx.Done），持有对 stale `*websocket.Conn` 的引用。反复重连 → goroutine 累积。
**修法**：使用 per-connection `context.WithCancel`（派生自 ctx），在 read loop 断开时 cancel 以释放旧 goroutine。

## 三、Spec 轴发现

### P1

**[Spec-P1-DOS] `agent/internal/updater/upgrade.go:217` — nuclei 下载无大小限制。**

与 Standards S-P1-2 重叠。Go 标准库 `io.ReadAll` 无内置限制，恶意 zip（即使来自内网）可 OOM agent。本项在 Spec 轴提出是因为「需求未定义下载大小限制」，属于 spec 缺失而非代码实现错误。

**修法**：需求文档化 `max_nuclei_download_bytes = 200 * 1024 * 1024`，Go 端加 `io.LimitReader`。

**[Spec-P1-RATE] `src/api/routers/vulnscan.py:209-242` — `batch-delete` 缺少请求大小限制。**

需求「批量删除扫描任务」未指定单次最大任务数。当前实现无上限，可构造 10000 个 task_id 的请求导致串行查删耗时数分钟。

**修法**：路由层加 `max(len(req.task_ids), 200)` 上限或 body size limit。

## 附：为何两轴

一个变更可能通过一轴而失败于另一轴：

- 代码符合所有标准但实现错了东西 → **Standards 过，Spec 不过**。
- 代码完全按需求做但破坏项目约定 → **Spec 过，Standards 不过**。

分开报告可防一轴遮蔽另一轴。本文件保留两轴独立结论；后续修复计划（必须统一去重）在 [后续计划V10.md](后续计划V10.md)。

## 附二：ruff format 全仓格式化说明

本次 diff 中 ~90% 的行变更为 `ruff format` 一次性全仓格式化。涉及改动：

- 多行函数签名（单行过长 → 每参数一行）
- Tuple/list 字面量（单行过长 → 每元素一行）
- Import 排序（`isort` 规则 `I001`）
- BOM 字符移除（`﻿` → 无，修复 Windows 编辑器遗留）
- 三元表达式换行（单行过长 → 多行）
- 文件尾换行（`W391` end-of-file-fixer）

格式化不改变任何逻辑。BOM 移除是一个正向安全改进（某些旧版编辑器把 BOM 当可见字符，导致 JSON/TOML 解析失败）。
