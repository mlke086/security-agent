## 二、Standards 轴发现

### P1

**[S-P1-1] `src/api/routers/users.py:81-110` — 审计日志 fire-and-forget，安全事件可能被 GC 静默丢弃。**
`_audit()` 是同步函数，用 `loop.create_task(audit_logger.log(...))` 调度异步审计写入，但**不持有任何引用**。CPython 对这类任务仅保留弱引用，官方文档明确警告任务可能「在执行中途消失」被回收。对 `user.create / user.delete.soft / user.delete.hard / user.password / user.restore / user.update` 而言，审计记录（安全产品的合规命脉）可能静默丢失。此外 `loop.is_running()` 在 FastAPI 请求内恒为 `True`，故 `else: loop.run_until_complete(...)` 是死代码；`asyncio.get_event_loop()` 是已弃用访问器（应用 `get_running_loop()`）。
**修法**：把 `_audit` 改为 `async` 并 `await`，或把任务存到模块级 `set` 并在回调里 `discard`。

**[S-P1-2] `src/api/routers/users.py:322-340` — `DELETE ?hard=true` 物理删除用户行，孤立审计链且跳过依赖检查。**
硬删执行 `DELETE FROM users WHERE username=$1`，不检查依赖行（其拥有的主机、提交的审批、创建的扫描任务）。审计日志把 `actor`/`target` 存为裸 username 字符串，硬删后**该用户出现的每条审计条目都成孤儿**，监管链断裂。叠加 S-P1-1，管理员可在无持久记录下移除用户。软删（默认）安全。
**修法**：硬删前拒绝仍作为 `actor`/`target` 出现在审计索引中的用户，或门禁到更高权限；至少先校验依赖行。

**[S-P1-3] `src/api/routers/vulnscan.py:116-133 / 419-433 / 672-700` — 每请求 `VulnscanStore()` 新建，泄漏 Elasticsearch 客户端（Shotgun Surgery ×3）。**
`VulnscanStore.__init__`（`store.py:151`）会新建 `AsyncElasticsearch(hosts=...)` 连接池。路由对 `list_vulns/get_vuln/get_host` 已用 `get_vulnscan_store()` 单例，但新增的 `target_groups` 解析、`group` 主机查找、`/host-stats` 却 `from src.agents.store import VulnscanStore; VulnscanStore().list_hosts(...)`，且从不 `.close()`。`/host-stats` 每 30s 被多运营者轮询 + `group` 过滤挂在每次 vuln-list 查询 + `target_groups` 在每次建任务时解析 → 耗尽 ES 连接/文件描述符。
**修法**：统一用已在作用域内的 `get_vulnscan_store()`，或提供不构造 store 的 `list_hosts`。

**[S-P1-4] `src/api/routers/vulnscan.py:414-437` — 新增 `group` 过滤静默截断结果。**
传入 `group` 时：取该组主机 → `store.list_vulns(...)` **不带 `limit`**（默认 200，`store.py:588`）→ 内存里按 `hostname in hostset` 过滤这 200 条。若该组漏洞 >200（或被其它过滤挤掉），运营者看到**非确定子集并可能漏掉严重发现** —— 漏洞跟踪产品的正确性缺陷。
**修法**：把主机名集合下推为 ES `terms` 过滤（服务端），而非对有上限的结果集做后过滤。

- **双 LLM round-trip**：`src/api/routers/chat.py:api_chat`（`:238`）总是先 `_classify`（1 次，`:101`），再二次分派 —— scan→`chat_completion(schema=ScanIntent)`（`:276`）、web→`_answer_with_web`（`:220`）、project→`_answer_with_docs`（`:143`）、chat→`_answer_freeform`（`:234`）。**每次输入 = 2 次 LLM**。另一条 `scan_chat.py:api_chat`（`:259`）更差：reply（`:283`）+ intent parse（`:289`）+ 后台标题（`:301`→`:137`）= **3 次/输入**。
- **持久化历史 ≠ 展示历史**：`chatAssistant`（`frontend/src/api/client.ts:450-476`）是 `ChatScan.handleSend` 每条消息调的（`ChatScan.tsx:210`），它做 `GET conversation` + `POST /api/v1/chat` 后返回 —— **从不持久化** user/assistant 轮次。`/api/v1/chat` 本身无状态（收 `conversation_id` 但从不写库，`api_chat` 无 DB 调用）。持久化只发生在 **scan-execute 确认路径** `chatConversation(activeId, body.intent_text, …)`（`ChatScan.tsx:168`），那是**另一次** LLM 调用产生**另一条**回复。净效果：普通问答刷新即消失；执行扫描时，落库的轮次文本与运营者刚看到的不同。**这正是 F2。**
- **误导注释掩盖 bug**：`client.ts:470-475` 注释称 *「F2 (2026-07-23): the unified /chat router already calls the LLM exactly once and the scan_conversation helpers persist the turn inside the scan_chat router.」* —— 两句皆不成立：`/chat` 调两次且不持久化；`chatAssistant` 从不调 scan_chat router。注释让回归难被发现。
- **端到端**：前（`ChatScan`）→ 后（`/api/v1/chat`）单会话已通，但普通聊天的后→持久化链缺失。

**[Spec-P1-TOKEN] Feature 2 / 令牌隐藏：被根目录泄漏的令牌文件削弱 —— 已在本会话修复。**
- 令牌列表/状态响应不暴露明文：`api_agent_token_status`（`agents.py:560`）只回 `token_hash_prefix`（哈希前 8 位）；无 `GET /enroll-tokens` 列表端点；创建时返回一次（可接受）。
- **泄漏**：`enroll_token.json`（仓库根、未跟踪、未 gitignore）含 `{"token":"h8s5lhmz-…-MkM", ...}`，一次 `git add .` 即入库，直接违背「令牌不得暴露」。令牌看似已过期（`expires 2026-07-29T09:51`）但泄漏向量仍在。
- **本会话已处置**：文件已删除，并加入 `.gitignore`（`/enroll_token.json`）。审查期间两轴独立发现此问题。

## 附：为何两轴

一个变更可能通过一轴而失败于另一轴：

- 代码符合所有标准但实现错了东西 → **Standards 过，Spec 不过**。
- 代码完全按 issue 做但破坏项目约定 → **Spec 过，Standards 不过**。

分开报告可防一轴遮蔽另一轴。本文件保留两轴独立结论；后续修复计划（必须统一去重）在 [后续计划V9.md](后续计划V9.md)。
