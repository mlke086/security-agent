# 后端分布式架构拆分方案

> 状态：方案设计（已修订，v5）　|　日期：2026-08-05　|　修订：2026-08-05 v5(v4 实施 21 步后回写——补 vulnscan/tasks/parse 反代、channel 常量化、preprocessing enqueue_event、conftest.py marker 等)
> 目标：把单体镜像 `secagent-api:0.1.0`（估 4–5 GB）按功能拆成多个小服务，
> 统一 API 入口，Nacos 配置按模块划分，更新 Dockerfile 与部署文件。

## 一、现状分析

### 1.1 当前架构（单体）

一个镜像 `secagent-api:0.1.0` 被 3 个服务共用（`deployments/prod/docker-compose.yml`）：

| 服务 | 启动命令 | 职责 |
|------|----------|------|
| `api` | `uvicorn src.api.main:app` | FastAPI 网关 + 18 个路由 + WS 网关 + lifespan 初始化(ES/PG/规则/TaskWorker/吊销监听) |
| `taskworker` | `python -c ... TaskWorker` | 消费 Redis Stream 的 vulnscan 任务，跑 LangGraph 子图 |
| `celery` | `celery -A src.common.celery_app worker` | HITL 审批超时兜底 |

- 部署：`network_mode: host`，中间件全指 `127.0.0.1`（生产目标 `192.168.18.156`）。
- 开发机 `192.168.80.101` 是中间件机（Nacos v3.2.2 / Milvus 2.4.17 / Neo4j 5 / Kafka 3.8.0 / PG 17.6 / Redis 7 / ES 8.15.0 / ClickHouse），**bridge 网络 + 端口映射**。
- 前端独立 nginx 镜像，`/api` 反代到 `secagent-api:8000`。

### 1.2 镜像膨胀来源（关键）

按“哪个模块拖了哪个重依赖”定位（`grep` 实测）：

| 重依赖 | 体积估算 | 实际使用位置 | 仅该位置用 |
|--------|----------|--------------|-----------|
| `sentence-transformers`(拉 torch) | **~2 GB** | `knowledge/graphrag/vector/embedding.py`（BGE-large-zh-v1.5，`local_files_only=True`，模型文件也打进镜像） | ✅ 全项目仅此一处 |
| `pymilvus` | ~50 MB | `knowledge/graphrag/` + `orchestration/memory/manager.py` | ✅ |
| `neo4j` | ~30 MB | `knowledge/graphrag/` + `orchestration/memory/manager.py` | ✅ |
| `langchain`+`langgraph`+扩展 | ~250 MB | `orchestration/`(子图) + `agents/chat_kb/` + `knowledge/models/adapter.py` | 部分 |
| `docker` SDK | ~20 MB | `execution/sandbox/executor.py` | ✅ |
| `aiokafka` | ~50 MB | `preprocessing/consumer.py` | ✅ |
| `elasticsearch`/`asyncpg`/`redis`/`fastapi` 等 | ~250 MB | 多处共享 | 共享 |

**结论**：torch（sentence-transformers）是膨胀主因，且仅 GraphRAG 调查链路用到；把它隔离出去，主链路镜像立省 ~2 GB。

### 1.3 模块耦合分析（路由 → 子系统）

| 路由 | 依赖子系统 | 重依赖 |
|------|-----------|--------|
| agents/monitor/users/rules/nuclei_templates/responses/alerts/stream/operations | agents + common | 无重依赖 |
| detection/sigma_rules | detection + common | 无 |
| demo | orchestration + api | langgraph（仅 demo） |
| **chat / scan_chat / models** | agents(chat_kb/conversation) + knowledge(LLM) + api store | langchain(chat 走 knowledge/models/adapter.py;chat_kb/engine.py 是纯关键字检索,无 langgraph 依赖) |
| **vulnscan** | agents(store) + **orchestration(子图)** + knowledge(LLM parse) | langgraph+langchain |

`vulnscan` 异步路径只 `enqueue_task`（轻，Redis），同步路径才直跑 `run_vulnscan`（重）。chat 的 LLM 调用走 `knowledge/models/adapter.py`(langchain);`chat_kb/engine.py` 顶层只 import 关键字检索与 ES,**无 langgraph 依赖**(实测:langgraph 只被 `src/orchestration/` 下 6 个文件 import)。

### 1.4 已有的分布式基础（关键利好）

WS 网关**已经用 Redis pub/sub 做跨进程总线**（`src/agents/ws_gateway.py`）：
- API 进程持有 WS 连接，`connect()` 时订阅 `agent:cmd:{agent_id}`，`_pubsub_consumer` 把 Redis 消息转发给本地 WS。
- taskworker 调 `gateway.broadcast()` → `redis.publish("agent:cmd:{id}", ...)`，API 进程转发给 agent。

→ **taskworker 早已是独立进程**，靠 Redis 与 WS 解耦。这意味着编排/扫描服务可以干净地拆出去，不必持有 WS 连接。

### 2.2 服务职责、依赖与镜像预估

| 服务 | 职责 | 主要依赖 | 镜像预估 |
|------|------|----------|----------|
| **gateway** | 统一入口、鉴权(JWT)、agent WS、enroll、规则分发、vulnscan 纯 CRUD(入队/列表/取消/SSE/findings/reports/batch delete/host stats/queue stats——不含 langgraph 子图)、detection、users、monitor、alerts、operations、responses | fastapi,uvicorn,asyncpg,redis,elasticsearch,httpx,jose,passlib,pydantic,structlog,watchdog,PyYAML,**langgraph**(若走方案 B 留 sync 调试)| **~500 MB**(若选 A 拆路由)/ **~550 MB**(若选 B lazy 兜底) |
| **ai** | /chat /scan-chat /models /vulnscan/tasks/parse:意图三分类、自由对话、系统问答、联网搜索、模型管理 | langchain,langchain-openai/anthropic,fastapi,asyncpg,redis,elasticsearch,httpx | **~350 MB** |
| **scan-engine** | 消费 Redis Stream 跑 LangGraph 流水线(vulnscan/investigation/responder/vuln_hunter)、事件流水线、向 agent 下发扫描(经 Redis)、沙箱执行 | langgraph,langchain,langchain-openai/anthropic,redis,asyncpg,elasticsearch,httpx,docker(沙箱) | **~500 MB** |
| **graphrag** | 向量嵌入(BGE)+Milvus 检索+Neo4j 图谱+会话记忆，HTTP 暴露 /embed /search /graph /memory | **sentence-transformers(torch)**,pymilvus,neo4j,fastapi,uvicorn | **~2.5 GB**（唯一重镜像） |
| **preprocessing** | Kafka 消费 EDR 告警→IOC 抽取→脱敏→推流水线 | aiokafka,redis,elasticsearch,httpx | **~280 MB** |
| **celery** | HITL 审批超时定时任务 | celery,redis,asyncpg | **~200 MB** |

对比现状：1 个 ~4–5 GB 镜像 → 主链路(gateway/ai/scan-engine)都在 ~500 MB 以内，torch 只存在于 graphrag。**注**:gateway 体积上调因实测 `vulnscan.py:26` 顶层 import 了 `subgraphs/vulnscan/graph.py`(`langgraph` 强依赖);除非阶段 2 采用关键改动点 3 的(A)拆路由方案把 sync 调用挪到 scan-engine,否则 gateway 镜像必含 langgraph。具体取舍见阶段 2 与决策点 13。

### 2.3 统一 API 入口与路由

- **对外只有一个入口**：前端 nginx → `gateway:8000`（保持现状的 nginx.conf upstream）。
- gateway 直接处理所有 CRUD/WS 路由；**LLM 类路由反向代理到 ai 服务**：
  - `/api/v1/chat` → `127.0.0.1:8001`(host 网络)/ `ai:8001`(bridge 网络)
  - `/api/v1/scan-chat` → 同上
  - `/api/v1/models` → 同上
  - `/api/v1/vulnscan/tasks/parse` → 同上
- **服务地址配置**：通过 env `AI_BASE_URL` 注入(默认 `http://127.0.0.1:8001`),避免 host 网络下 compose 服务名 DNS 不解析导致启动失败;bridge 版 compose 用 `AI_BASE_URL=http://ai:8001` 覆盖。graphrag 同理:`GRAPHRAG_BASE_URL`(默认 `http://127.0.0.1:8002`)。
- 代理时透传 `Authorization`；ai 服务用同一 `API_SECRET_KEY` 自验 JWT（微服务标准做法）。
- WS(`/api/v1/agents/ws`)、SSE、其余 `/api/v1/*` 全留在 gateway。
- scan-engine / graphrag / preprocessing / celery **不直接对外暴露**，仅内部 HTTP/Redis 通信。

> 备选：nginx 直接按路径分流到 ai。但统一走 gateway 更利于鉴权/审计/CORS 一致性，推荐 gateway 代理。

## 四、服务间通信设计

| 通信路径 | 方式 | 说明 |
|----------|------|------|
| nginx → gateway | HTTP/WS | 唯一对外入口 |
| gateway → ai | HTTP 代理 | `/chat` `/scan-chat` `/models` `/parse`，透传 JWT；**enqueue 仍由 gateway 完成**(ai 服务 parse 只返回 LLM 抽取的 task spec,gateway 收到后调本地 `task_queue/enqueue.enqueue_task` 入 Redis Stream) |
| gateway → scan-engine | Redis Stream | vulnscan 任务入队(沿用 `enqueue_task`,gateway COPY `task_queue/` 包,`__init__` lazy 化后无 langgraph 链(见改动点 7));事件 `/api/v1/events` 改为入队 |
| scan-engine → gateway(WS) | Redis pub/sub | `agent:cmd:{id}` 下发扫描命令(沿用,gateway 转发给 agent)**无需改动** |
| scan-engine → graphrag | HTTP | embed / 向量检索 / 图谱查询 / 记忆(替代直连 milvus/neo4j);`GRAPHRAG_BASE_URL` 默认 `http://127.0.0.1:8002` |
| ai → graphrag | HTTP | (若 chat 需要知识库检索;当前 chat 走 docs+ES,可暂不接 graphrag) |
| preprocessing → scan-engine | **Redis Stream**(定型)| 告警事件入独立 `events:tasks` stream(与 `vulnscan:tasks` 分流,避免两种流水线消费者逻辑混杂);`preprocessing/consumer.py` 的 `_emit()` 改为调 `src.orchestration.task_queue.enqueue.enqueue_event` 推 `events:tasks`,scan-engine 同 worker 不同 consumer group 消费 |
| 全部 → PG/ES/Redis | 直连 | 共享存储,连接串走 Nacos/env |

### 5.3 nacos_loader 改造

`src/common/config/nacos_loader.py` + `settings.py`：支持每个服务加载多个 dataId。
- env 增加 `NACOS_DATA_IDS=security-agent-shared.yaml,security-agent-gateway.yaml`（逗号分隔）。
- `load_nacos_settings()` 循环 fetch 每个 dataId，合并后 `apply_nacos_overrides`。
- **Settings 新增字段**(阶段 0 前置):在 `src/common/config/settings.py` 加 `ai_base_url: str = "http://127.0.0.1:8001"` 与 `graphrag_base_url: str = "http://127.0.0.1:8002"`,否则 `nacos_loader` 走白名单逻辑会把纯 env 字段过滤掉,默认值不可用。`PROTECTED_OVERRIDE_KEYS` 白名单不变。
- **多 dataId 热更新**:`start_nacos_listener()` 改为轮询所有 `NACOS_DATA_IDS`(当前实现只单 dataId 轮询,不改则热更新只跟一个配置,其他服务配置改了感知不到)。**改造方案选型**:
  - **(推荐) 方案 A(合并指纹)**:每次循环遍历 `NACOS_DATA_IDS`,逐个 fetch + 合并为一个 dict,`_config_fingerprint` 取合并后字典的序列化 hash。**优点**:reload 时 `apply_nacos_overrides` 一次合并完成,settings 单例一次重建,无部分更新风险。**缺点**:任一 dataId 变更都触发 reload(对其他无变化的字段也走一遍 apply)。
  - **(可选) 方案 B(独立监听)**:每个 dataId 启一个 `_poll()` task,各自维护 fingerprint,各自 reload。**优点**:单 dataId 变更精确触发。**缺点**:并发 reload 时 settings 单例被并发重建,需加 asyncio.Lock;且 reload 中 `apply_nacos_overrides` 会用合并前 dict 覆盖,可能丢字段(中间状态漏合并)——除非按顺序串行 reload,**实际工程上得不偿失**。
  - **结论**:选方案 A,settings 单例一次重建语义最清晰。
- `Settings` 单例仍是全量字段（各服务字段超集），未用字段忽略；保持 `case_sensitive=False` 与白名单逻辑不变。
- 向后兼容：未设 `NACOS_DATA_IDS` 时回退到单 `NACOS_DATA_ID`（旧部署不破坏）。

## 九、关键决策点（已确认 2026-08-05）

1. **嵌入策略**：✅ graphrag 作为独立重服务（torch 只存在于该镜像；BGE 模型与 Milvus 索引不变，改动最小）。
2. **拆分粒度**：✅ 全拆 6 服务（gateway / ai / scan-engine / graphrag / preprocessing / celery）。
3. **沙箱**：✅ 留在 scan-engine 内（docker SDK ~20MB，随 responder 子图，不强拆）。
4. **网络模型**：✅ 生产继续 host 网络（兼容 192.168.18.156 单机部署）；另附 bridge 版 compose 适配 192.168.80.101 类中间件机。
5. **enqueue 落点**：✅ gateway 完成入队（ai 仅返回 task spec）；gateway COPY `task_queue/` 包(`__init__` 的 runner/worker import 改 lazy 后不拖 langgraph,见改动点 7)。**新增长期函数 `enqueue_event`**(preprocessing->scan-engine 用)。
6. **celery 兜底超时(非 pub/sub)**：✅ celery 是纯后台 worker；所有审批 HTTP(列/通过/驳回)走 gateway ops 路由。超时分两层:① 主超时=scan-engine 的 `approval_store.wait_result()` deadline 阻塞,到点自调 `resolve(id,"timeout")` 写 PG(现状不变);② celery 当**兜底**--审批创建时 `approval_timeout_task.apply_async(countdown=timeout+buffer)`,scan-engine 正常时 `wait_result` 已先行 resolve(celery task 命中终态幂等 no-op),scan-engine 崩溃/重启致 `wait_result` 丢失时由 celery 兜底 resolve。**不用 pub/sub**(无延迟语义;且 `approval_timeout_task` 当前是死代码零调用方,本方案首次接通)。
7. **store 索引与表名**:✅ 保持硬编码(`agents/store.py` 的 `INDEX_*` 模块级常量),本轮不配置化(Nacos 只承担连接串,不动 schema/索引命名,改动最小避免越界)。
8. **ai 服务回滚降级**：✅ 过渡期保留双轨(env `AI_PROXY_ENABLED` 切换),代理失败返回 503 + Retry-After + 监控指标。
9. **base 镜像锁定**：✅ base 不 COPY 源码；版本锁定到 `requirements/base.txt` 与 `requirements/<service>.txt`。
10. **embedding 失败策略**：✅ fail-fast,严禁静默降级;模型文件推荐 volume 挂载 + entrypoint 存在性检查。
11. **监控与日志**：✅ 每个服务 `/metrics`(prometheus_client) + structlog JSON 日志；告警指标列表见阶段 5。
12. **回滚剧本**：✅ 旧镜像 tag 保留 + 旧 compose 归档 + Nacos 旧 dataId 保留 7 天；每阶段起动前 docker tag `:prev`。
13. **vulnscan 路由归属(A/B 方案选型)**:✅ gateway 不能整路由留 vulnscan.py——实测 `vulnscan.py:26` 顶层 `from src.orchestration.subgraphs.vulnscan.graph import run_vulnscan`,`graph.py:3` 顶层引 langgraph 且 import 时构建 StateGraph,必然拖入 gateway 镜像。两种落地方式:
    - **方案 A(推荐)**:把 `api_create_task`(含 sync 分支)、`api_task_findings`、`api_get_report` 等真调 langgraph 的端点迁到 `src/scan_engine/routers/vulnscan.py`(新建),由 gateway 代理 `/internal/vulnscan/*`;gateway 只保留 CRUD。gateway 镜像 ~500MB,与 scan-engine 同档但职责清晰,迁移成本可控。
    - **方案 B(过渡)**:保留 sync 调试分支在 gateway,必须把 vulnscan.py:26 import 改为函数内 lazy(用 `if sync:` 守护),admin 调 `?sync=1` 才加载 graph;**生产关闭 sync 入口后建议同步删除 sync 分支整体**(admin 调试入口为遗留)。gateway 镜像 ~550MB。
    - **建议执行顺序**:阶段 2 上线前二选一定型;若选 B,阶段 2 末尾加 TODO 在阶段 3/4 期间清理 sync 分支,避免长期带 langgraph。
