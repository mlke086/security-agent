## 关键结论

### 1. vulnscan.py:26 顶层 import graph.py——P0 已纳入方案 A(阶段 2 处理)

实测:`src/api/routers/vulnscan.py:26` 顶层
`from src.orchestration.subgraphs.vulnscan.graph import run_vulnscan`,
而 `graph.py:3` 顶层 `from langgraph.graph import END, StateGraph` 且
`compiled_vulnscan_subgraph = get_vulnscan_subgraph()` 在 import 时即构建。
**gateway 镜像带 vulnscan.py 必拖 langgraph**。方案 2 阶段 2-3 按决策点 13 方案 A 处理:
- 删除 vulnscan.py:26 顶层 import
- 删除 sync 分支(197–228 行)
- 端点拆分:langgraph 端点(api_create_task 含 sync、api_task_findings、api_get_report)
  迁到 `src/scan_engine/routers/vulnscan.py`,由 gateway 代理

### 2. hitl_handler.py 第 129 行 lazy import execution.actions——gateway 潜在风险

实测:`src/orchestration/subgraphs/responder/hitl_handler.py:129` 在某函数体内
`from src.execution.actions import ActionContext, ActionDispatcher`。

- **当前状态**:lazy 在函数内,gateway 携带 hitl_handler 不立即拖 execution/docker SDK。
- **当前 ops 路由使用**:`list_pending_approvals`/`resolve_approval_by_event_id`/`_add_pending_approval`,
  都不触发 lazy path,**gateway 安全**。
- **未来风险**:ops 路由新增端点调用 dispatcher 时,gateway 会突然带 docker SDK。阶段 5 收尾时
  应固化 lint 规则禁止 hitl_handler.py 在 lazy path 外引 execution。
