## 一、需求①：Agent 性能监控

### 1.1 现状与缺口（已核实）

| 环节 | 现状 | 证据 |
|------|------|------|
| Agent 采集 | `resource/monitor.go` 已用 gopsutil 每 10s 采样 CPU/mem，但 `Usage()` **从未被任何发送方调用**；`protection/protection.go` 仅本地阈值判断（CPU/load/mem/disk） | agent 2 报告 |
| Agent 上报 | 心跳 `client.go:351-363` 的 cpu/mem 在 V13 P2-19 **已被删除**（原为硬编码 0 占位），注释误称“real usage reported via protection/resource”——实际二者都只本地用 | `client.go:358-361` |
| 服务端接收 | `ws_gateway.handle_message`（`ws_gateway.py:257-289`）只分派 `heartbeat/scan_step/scan_result/task_ack/update_ack/response_ack/monitor_event`，**无 `resource_metrics` 分支** | agent 1 报告 |
| 服务端存储 | `monitor_store.py` → ES `secagent-monitor` 只存**进程快照**（无 cpu/mem/disk/net 字段）；全仓库无任何主机性能指标存储 | agent 2 报告 |
| 前端 | `/metrics` 端点与 `getMetrics()` 是**事件/LLM 队列指标**，非主机资源指标；HostOnboardPage 有“进程监控”抽屉但无性能趋势 | client.ts:81 |

**结论**：整条“采集→上报→存储→查询→展示”链路都缺失，需完整新建。好在 gopsutil 依赖已存在、WS 通道已建好、`monitor_store` 的 ES 写入模式可直接复用，工程量集中在“接线”。

### 1.2 总体设计

```
Go Agent                                    gateway(:8000)                    前端
┌──────────────────────┐   WS host_metrics   ┌────────────────────────┐   GET /agents/{id}/metrics
│ resource/monitor.go  │ ───────────────────▶ │ ws_gateway.handle_msg  │ ◀──────────────────────▶ HostOnboardPage
│  + metrics 采集器     │  (每 15s，可配置)     │  └ _handle_host_metrics│
│  cpu/mem/disk/net    │   断线丢弃(不入离线队列)│      └ metrics_store   │   ES secagent-hostmetrics
│  gopsutil(已有依赖)   │                      │         写入 ES          │   (时序，30d 保留)
└──────────────────────┘                      └────────────────────────┘
   config_update 下发 metrics_interval_sec         /agents/{id}/metrics?range=1h|24h|7d
                                                    /agents/{id}/metrics/latest
```

**设计要点**
- **采集频率独立于心跳**：心跳 ~30s 且承载版本/在线语义；性能指标用独立 `host_metrics` 消息、独立间隔（默认 15s），互不耦合。
- **断线丢弃不入离线队列**：性能指标是高频时序数据，离线累积重连续传会洪泛且陈旧无价值。与 `scan_result`（必须可靠投递）相反，`host_metrics` 走“连上才发、断开即丢”。
- **存储用 ES（v1）**：复用现有 ES 客户端与 `monitor_store` 写入模式，零新中间件。中等体量（100 主机×15s≈57.6 万/天）ES 可承载 + 30d 保留清理。规模超 500 主机或保留>90d 时再迁 ClickHouse（已部署但未接入，见 §1.6）。
- **前端复用“进程监控”抽屉模式**：HostOnboardPage 已有 `MonitorOutlined`+`Drawer` 的成熟范式，性能监控照搬。

## 二、需求②：内网资产扫描（agentless，fscan 类）

### 2.1 需求分析与参考项目

**需求**：不需装 Agent，输入网段(CIDR)/主机 IP，自动扫描网络存活、端口、应用/服务，匹配漏洞，AI 分析后输出最终结果。

**参考项目流程对照**（fscan / Luyos-Network_scanner / ss0t-Scan 共同的流水线）：

| 阶段 | fscan 做法 | 本方案做法 |
|------|-----------|-----------|
| 主机存活 | ICMP/TCP ping | nmap `-sn`（含 arp） |
| 端口扫描 | 自研高并发 TCP | masscan（快，全端口扫）+ nmap（准，top ports/-p） |
| 服务识别 | banner grab | nmap `-sV`（版本/CPE）+ HTTP 指纹（title/server/favicon hash/技术栈） |
| 漏洞匹配 | 内置 POC | CPE→CVE 规则库（复用现有 CVE 规则）+ nuclei 模板（复用现有模板库）+ 可选 fscan POC |
| 爆破（可选） | 内置弱口令 | 可选模块（ssh/smb/redis 等弱口令），默认关 |
| 结果 | 文本输出 | ES 存储 + AI 分析 + HTML 报告 |

**结论**：用“nmap/masscan/nuclei 模块化组合”实现 fscan 的流水线，比直接套 fscan 二进制更可控、输出结构化、AI 友好；fscan 二进制可作为“快速模式”引擎可选集成。

### 2.2 架构评估：是否独立服务（决策）

**结论：新增独立 `asset-scan` 服务（第 7 个服务）。** 理由：

1. **依赖隔离**：nmap/masscan/fscan 是大型平台相关二进制（apt 包 / Go 构建），塞进 scan-engine 会让 LangGraph 镜像（~500MB）显著膨胀且引入系统包依赖。这与既有拆分哲学一致（graphrag 为 torch 隔离、preprocessing 为 aiokafka 隔离）。
2. **运行时隔离**：agentless 扫描是网络/CPU 密集、长时运行（扫 /24 全端口 + nuclei 可达数十分钟），独立服务避免拖垮 agent vulnscan 流水线（后者有 SLA 敏感的 HITL 超时与实时 SSE 期望）。一个失控的 /16 扫描不应饿死 agent 扫描任务。
3. **部署灵活性**：agentless 扫描需从“对目标网段有网络可达性”的主机发起——往往不是中心控制台，而是目标网络区的专用扫描节点。独立服务可部署到专用扫描主机（控制台 gateway 未必有到所有内网段的直连路由）。
4. **安全隔离**：outbound 扫描是特权网络操作，独立容器/服务便于收敛防火墙规则（仅 asset-scan 需放行出站扫描），缩小爆炸半径。
5. **复用而非绿地**：task_queue 模式（新 Stream）、ES store 模式、SSE、LLM adapter、nuclei 模板库、CVE 规则库均可复用，新服务主要是“扫描执行 + 编排”。

**备选（不推荐，作为降级方案）**：作为 scan-engine 的新任务类型（`asset_scan` subgraph + TaskWorker 新 consumer group），把 nmap/masscan 加进 scan-engine Dockerfile。省 1 个服务，但牺牲上述隔离性，且 scan-engine 镜像膨胀。若团队坚持最小服务数可走此路，本方案的服务划分与子图设计可平移。

### 2.5 扫描引擎设计

**`discover` 节点**
- 主机存活：`nmap -sn -n <cidr>`（ICMP/arp；纯内网 arp 高效）。
- 端口扫描：`masscan --rate=2000 -p1-65535 <ip>`（快，全端口）或 `nmap -sS --top-ports 1000`（准）。`engine=fast` 用 masscan，`engine=full` 用 nmap，`engine=global` 两者叠加。
- 解析 XML/JSON 输出 → 存活主机 + 开放端口列表 → 写 `assetscan-assets`。
- **并发与限速**：masscan `--rate` 可配；nmap `--max-rate`。大网段分块（如 /16 拆 /24）串行/有限并发，避免网络风暴。

**`fingerprint` 节点**
- `nmap -sV -sC <ip> -p <ports>`：服务版本 + CPE + 默认脚本（banner/产品）。
- HTTP 服务：发请求取 title/server header/状态码；favicon hash（mmh3）；技术栈（可选 wappalyzer 风格关键字）。
- 输出：每 (ip,port) 的 service{name,product,version,cpe,banner,http_title}。

**`match_vulns` 节点**
- **CPE→CVE**：用 nmap 输出的 CPE（如 `cpe:/a:nginx:nginx:1.18.0`）查现有 CVE 规则库（`src/agents/rules_sync` 维护、存 ES/PG 的规则），版本区间匹配 → 候选漏洞。复用现有 matcher 的 `versionCompare` 逻辑思路（服务端实现一份）。
- **nuclei 模板**：对 HTTP 服务跑 nuclei（复用已管理的模板库 `nuclei_templates.py` + 镜像内 nuclei 二进制），`-severity critical,high,medium`，结果结构化。
- **可选 fscan POC**：`engine=fast` 可调 fscan 二进制做常见未授权/弱口令 POC（爆破默认关）。
- 输出：每 (ip,port,cve/template_id) 的 vuln{severity, evidence, fix} → 写 `assetscan-vulns`。**此处 severity 为原始扫描结果**（与需求③一致语义）。

**`llm_analysis` 节点**（复用 vulnscan `llm_analysis` 模式，`nodes.py:825`）
- 分批（15/批）过 `get_model_adapter()`：对每批漏洞做二次过滤/定级/误报剔除/修复建议（`chat_with_retry` + 失败补扫队列）。
- 资产维度：LLM 汇总资产风险排序、暴露面分析、横向风险提示。

**`generate_report` 节点**（复用 vulnscan `generate_report` 模式，`nodes.py:1110`）
- 统计摘要 + 资产清单 + 漏洞明细 + 修复建议 + LLM 总体研判 + HTML 导出。

### 2.6 AI 分析与报告
- LLM 适配器复用 `src/knowledge/models/adapter.py`（走 `llm_models` PG 表，支持 DeepSeek/Claude/OpenAI/vLLM）。
