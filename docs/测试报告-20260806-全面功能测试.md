## 二、测试中发现并修复的 Bug(5 个后端 + 2 处前端 e2e 环境)

### P0-1:gateway proxy_router 注册顺序吞路由(src/api/main.py)
- **现象**:`/api/v1/alerts`、`/api/v1/detect/rules` 等返回 404 "not a proxied ai route"
- **根因**:proxy 的 catch-all `/api/v1/{full_path:path}` 注册在 alerts/detection router **之前**,FastAPI 按注册顺序匹配,先命中 catch-all
- **修复**:`include_router(proxy_router)` 移到所有具体 router 之后(注册顺序=匹配优先级)
- **验证**:修复后 alerts/detect 恢复 200

### P0-2:事件 trace 永远为空(src/api/store_es.py)
- **现象**:事件状态 completed、tags 齐全,但 trace 接口永远 0 条(前端"暂无推理轨迹")
- **根因**:audit index 的 `event_id` 实际 mapping 是 **keyword 类型(无 .keyword 子字段)**,但 `_fetch_trace` 用 `term: {event_id.keyword: ...}` 查询 → 永远 0 命中。**数据其实一直在写**(实测事件有 7 条 trace),纯读取 bug
- **修复**:查询改为 `bool should` 双条件(`event_id` + `event_id.keyword`),兼容两种索引形态
- **验证**:`7679e9e7` trace 0 → 7 条,gateway API 返回完整推理轨迹

### P0-3:demo seed 500 — approval_id 非 UUID(src/api/routers/demo.py)
- **现象**:`POST /api/v1/demo/seed` → 500,但事件已部分写入
- **根因**:demo 生成 `ap-{8hex}` 作为 approval_id,但 `approvals.approval_id` 是 **UUID 列** → asyncpg `invalid UUID`
- **修复**:改用 `str(uuid.uuid4())`
- **验证**:修复后 injected=5,approvals 列表出现 3 条真实 L3 审批

### P1-4:events consumer NOGROUP 死循环(src/scan_engine/main.py)
- **现象**:stream 被运维清理删除后,consumer 每秒报 `NOGROUP` 错误,永不恢复(直到进程重启)
- **根因**:`xgroup_create` 只在启动时做一次;stream 运行中删除后 `xreadgroup` 永久 NOGROUP,`except` 只记日志重试
- **修复**:NOGROUP 时幂等重建 group(mkstream=True)
- **验证**:删除 events:tasks 后 4s 内自动重建(1 consumer 在线);TaskWorker 侧 ensure_group 本就幂等,自动恢复

### P1-5:graphrag memory/search 503 — Milvus 连接交叉断开(src/knowledge/graphrag/vector/milvus_client.py)
- **现象**:`/memory/search` 503 `ConnectionNotExistException`;`/vector-search` 正常;独立进程调用正常
- **根因**:graphrag 服务内 GraphRAGEngine 用完 `close()` 断开 pymilvus **全局 default 连接**,MemoryManager 复用同一连接池时 `Collection()` 失败
- **修复**:`MilvusVectorClient` 加 `_ensure_connected()`(幂等重连),在 search/insert/delete_by_event 前调用
- **验证**:memory/search 恢复 200

### 前端 e2e 环境修复 1:后端无 PG 凭据致登录 401(frontend/playwright.config.ts)
- **现象**:Playwright e2e 5/6 失败,全部卡在登录(唯一通过的"错误密码"用例因 401 也显示错误提示)
- **根因**:webServer 启动后端只设了 `STORE_BACKEND=memory`,**没设 `PG_PASSWORD`** → 后端连不上 PG → `get_user()` 返回 None → admin/admin123 登录 401
- **修复**:webServer command 改为 `seed_e2e_users.py && uvicorn`,env 补 `PG_HOST/PG_PORT/PG_DATABASE/PG_USER/PG_PASSWORD`;新增 `scripts/seed_e2e_users.py`(bcrypt 直接哈希,重置 admin123/analyst123/viewer123/responder123,幂等 UPSERT)
- **验证**:修复后 4/6 通过

### 前端 e2e 环境修复 2:过时用例(frontend/e2e/app.spec.ts)
- **现象**:剩 2 个用例失败——"注入演示数据"按钮找不到(该功能已移除);`/扫描/` 正则同时命中"扫描任务"与"扫描报告"(strict mode violation)
- **修复**:用例 4 改为验证"事件队列"菜单导航;用例 6 改为精确匹配"扫描任务"菜单
- **验证**:6/6 全部通过(21.3s)

## 三、跨服务链路验证(核心拆分成果)

1. **vulnscan 全链路**:gateway `POST /tasks` → Redis Stream `vulnscan:queue:tasks` → scan-engine TaskWorker 消费 → LangGraph 子图执行 → ES 状态回写(queued→running→completed)→ gateway 查询 ✅
2. **事件流水线**:gateway `POST /api/v1/events`(入队,不直跑 LangGraph)→ `events:tasks` stream → scan-engine events consumer → `run_pipeline`(triage→investigation→aggregation)→ trace 7 步可查 ✅
3. **LLM 链路**:gateway chat/parse 反代 → ai 服务 → LLM 三分类/意图解析(真实模型调用成功)✅
4. **图谱链路**:scan-engine cti_analyst → graphrag HTTP(embed/vector/graph 全通)✅
5. **审批链路**:demo 注入 L3 审批 → approvals 表(PG)→ 列表可查 ✅
6. **监控**:三服务 /metrics(ai_unreachable_total/graphrag_embed_latency/taskworker_lag)✅
