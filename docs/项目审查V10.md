## 二、Standards 轴发现

### P1

**[S-P1-1] `src/orchestration/task_queue/enqueue.py` 与 `src/agents/ws_gateway.py` 等多处仍以 `asyncio.create_task(...)` 提交后台任务但**不持有引用**。**

V9 P1 修复把 `users._audit` 改成 `async + await`，但同会话的其他后端路径仍是 fire-and-forget：

- `enqueue_task` 路径下的 Redis publish / progress 上报若 fire-and-forget 同样可被 GC 丢弃（运行时即静默失败）。
- `ws_gateway.send_to_agent` 的 `try/finally` 路径里仍出现 `asyncio.create_task(_record_response_ack(...))` 这种提交模式（如有）。
- `run_vulnscan` 在 `vulnscan.py` 中通过 `asyncio.create_task(...)` 触发 subgraph 的情况。

**修法**：和 `_audit` 一样改为 `await`，或维护模块级 `_BG_TASKS: set` 在回调里 `discard`。参考 V9 的 `_audit` 改法（`src/api/routers/users.py:84-99`）。

**[S-P1-2] `src/api/auth/jwt.py` 与 `src/api/routers/users.py` 中 `passwordForm` / `passwordOpen` 等历史状态字段残留。**

`AppLayout.tsx` 在 `dba9c5ea`（housekeeping）中被移除了密码修改 UI，状态与 `useForm` 都已删，但 `ac8ffb6a` 抽出 `ChangePasswordModal` 后，**`AppLayout.tsx` 没有把 `<ChangePasswordModal>` 重新挂上**（HEAD 与新组件并存却无消费方）。这意味着：未来若有人重新启用密码修改入口，最容易的路径是把 inline Modal 粘回去，让 V9 4.5 的抽取工作白做。

**修法**：要么把按钮 + `<ChangePasswordModal>` 一并接回去（推荐，最小代价），要么先删 `ChangePasswordModal.tsx` 直到真的需要为止。

**[S-P1-3] `src/orchestration/subgraphs/vulnscan/nodes.py` 内 `llm_analysis` 异步 helper 把 `get_model_adapter()` 与后续 `chat_completion(...)` 调用包在 `try/except Exception` 里，但**仍 fire-and-forget 实际写入**：`update_vuln(..., ai_processed=False, ai_reason="LLM 不可用")` 在 fallback 分支（`:467-486`）和批失败 fallback 分支（`:570-585`）出现两次，且第二次失败时由于异常已吞掉，写入失败也无人察觉。**

**修法**：抽 `_write_fallback(findings, reason)` 一次（V9 阶段 4.3 已规划，未交付），并在 helper 内同样 `try/except + logger.warning` 而不是 fire-and-forget。

**[S-P1-4] `src/agents/rules_sync.py` `import asyncio` 顶层化（V9 4.3 已交付），但同文件 `_asyncio.Semaphore(20)` 在函数内被替换为 `asyncio.Semaphore(20)` 后，`asyncio` 模块本身未在任何被引用路径上"显式 await"过该 Semaphore —— 即抽完之后该 Semaphore 实例 `sem` 在函数体内未使用。**

**修法**：删去未使用的 `sem` 变量，或真正用于批并发限制（`asyncio.gather` 传入 `sem`）。

## 三、Spec 轴发现

### P1

**[Spec-P1-FILTER] `src/agents/store.py:585-640` `list_vulns` 签名膨胀到 11 个可选 kwargs，`cve/cve_keyword/hostname_keyword/name_keyword/ai_processed/date_from/date_to` 成团穿梭路由与 store —— V9 后续计划阶段 4.3 明确规划「捆进 `VulnFilter` dataclass」**未交付**。**

VulnFinding + 7 个 filter 字段再加 task_id/hostname/hostnames/severity/status/limit/offset 共 14 个参数。任何新增 filter 必须同时改路由、store、测试三处 —— Shotgun Surgery 的教科书场景。

**修法**：

```python
@dataclass(frozen=True)
class VulnFilter:
    task_id: str | None = None
    hostname: str | None = None
    hostnames: list[str] | None = None
    severity: str | None = None
    status: str | None = None
    cve: str | None = None
    cve_keyword: str | None = None
    hostname_keyword: str | None = None
    name_keyword: str | None = None
    ai_processed: bool | None = None
    date_from: str | None = None
    date_to: str | None = None
    limit: int = 200
    offset: int = 0
```

路由层在 `query_params` → `VulnFilter` 间做转换，store 只接受 dataclass。

## 附：为何两轴

一个变更可能通过一轴而失败于另一轴：

- 代码符合所有标准但实现错了东西 → **Standards 过，Spec 不过**。
- 代码完全按 issue 做但破坏项目约定 → **Spec 过，Standards 不过**。

分开报告可防一轴遮蔽另一轴。本文件保留两轴独立结论；后续修复计划（必须统一去重）在 [后续计划V10.md](后续计划V10.md)。
