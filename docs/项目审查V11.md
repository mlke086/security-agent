### P1

**[S-P1-1] src/orchestration/subgraphs/vulnscan/nodes.py:380-385 _pub_progress 每次调用都新建 Redis 客户端 (ioredis.from_url) 并 close，未走任何连接池。**

V10 阶段 1 把 enqueue.py 的 fire-and-forget 全部 await 化、V10 ggregate 节点提取了 _write_fallback 复用模式，但 V11 新增的 _pub_progress（在 parse_intent、dispatch、collect、aggregate、llm_analysis、generate_report、cancel 节点中各调用一次）反方向退化：每个进度事件都"建连 → publish → 断连"，按 30 个 findings × 6 个节点 = 180 次/任务的连接抖动。WebSocket 推送端会看到 publish 延迟在 5–20ms 间漂移。

**修法**：模块级懒加载单例 _redis: aioredis.Redis | None = None，与 _pub_progress 共享；或在 main_graph 的 lifespan 里注入 pubsub_redis 依赖。generate_report 末段 wait r.delete(f"vulnscan:collect:{task_id}") 同样适用。

**[S-P1-2] src/orchestration/subgraphs/vulnscan/nodes.py:206-216 dispatch 在 engine == "global" 分支里既调 roadcast() 又调 send_to_agent()（per-agent nuclei），且

注释 "matcher/global use a single broadcast -- nuclei needs the resolved per-agent IP" 解释了设计意图，但

**修法**：

**[S-P1-3] gent/internal/scan/nuclei/portdiscovery.go:24-32 discoverListeningPorts() 失败时（ss 不存在 + /proc/net/tcp 读不到）静默返回

错误信息丢失 = 静默失败反模式。最小容器镜像（distroless、scratch）通常既没 ss 也没 /proc/net/tcp 暴露（即使是 host 模式容器可能也没 /proc），agent 部署在 distroless 镜像上即踩坑。

**修法**：返回 (ports []string, err error)，runner.go 在 err != nil 时给当前 task publish 一条 scan_step 事件，状态 reason 写 "port_discovery_failed: ss and /proc/net/tcp both unavailable"，同时仍然把"已 listen 端口未发现"作为一个 task 级 finding（info 级别）以保证 0 findings 不会让操作者误以为"无漏洞"。

**[S-P1-4] src/api/routers/chat.py:91-105 _classify 把所有异常（包括 ModelNotFoundError、网络中断、JSON 解析失败、timeout）都降级为 IntentDecision(intent="chat", confidence=0.0)，用户即使输入"立即隔离主机 web-01"或"删除全部告警"也会被路由到 free-form chat，不产生审计、不触发拦截。**

V10 修复了 chat 持久化、ScanIntent 提取，但 V11 引入 ModelNotFoundError（用户指定已删除模型）会进入同一降级路径，UI 不会知道分类失败。
eason=str(exc) 写入 IntentDecision.reason 但被 router 丢弃（仅 intent/confidence/reply/sources 进入响应），运维无可见信号。

**修法**：
- 区分"模型返回低置信度"（保持 chat 路由）与"分类器本身异常"（返回 503 + 告警 + 审计"classification_failed"事件）。
- 对 ModelNotFoundError 显式 HTTPException(503, "model_id not available")，让 UI 显式提示。
- _classify 返回的
eason 字段应透传到 SSE 进度 + audit。

**[S-P1-5] src/agents/chat_search/web_search.py:268-273 NVD 调用 httpx.AsyncClient(proxy=...) 实际参数名是 proxy（httpx < 0.28）或 proxies（httpx >= 0.28）；pyproject.toml 未固定 httpx 版本，升级后 proxy= 会被静默忽略，NVD 流量绕过企业代理直连公网。**

httpx 0.28 已发布（2024-11），主分支 changelog 把 proxies= 改为 proxy=（单数），但要求 Python 3.9+；我们这边 Python 3.12，两套 API 名称均存在。这是个 "depend on call order / version" 的脆弱接口。在企业内网部署下，NVD 走直连 = 流量绕审计 + 可能的 eDRP 告警。

**修法**：固定 httpx>=0.27,<0.29 区间（与 langchain_* 兼容性窗口一致），或在调用处 try/except TypeError 兼容两套接口；测试中加一个 proxy smoke（httpx.AsyncClient(proxy=...) 起得来就 OK）。

**[S-P1-6] src/api/routers/nuclei_templates.py:73-92 pi_import_zip 只校验 zip 可解压 + namelist 非空，**对 zip 大小 / 单文件数 / 解压后总字节数均无上限**。前端 NucleiTemplateViewer.tsx 走"上传 zip"按钮，恶意运维可上传 10GB zip 让后端 wait file.read() 占满内存后 parse_templates_zip 又 inflate 一份（13k 个 yaml 模板 ~50-200MB 是合法场景，但攻击者可构造嵌套 zip 炸弹解压到 GB 级）。**

- pi_sync_from_mirror 拉到的 zip 在 _ingest 前先看 len(zip_bytes)，超过 500MB 拒绝并 udit_logger.log("oversized_templates_zip", ...)。

## 附：为何两轴

一个变更可能通过一轴而失败于另一轴：

- 代码符合所有标准但实现错了东西 → **Standards 过，Spec 不过**。
- 代码完全按需求做但破坏项目约定 → **Spec 过，Standards 不过**。

分开报告可防一轴遮蔽另一轴。本文件保留两轴独立结论；后续修复计划（必须统一去重）在 [后续计划.md](后续计划.md)。
